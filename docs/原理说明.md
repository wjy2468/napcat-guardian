# 原理说明

本文解释"为什么会被踢""为什么保活不是银弹"，以及看门狗为什么这么设计。

---

## 一、掉线有三种完全不同的形态

很多人把所有掉线都当成"空闲被踢"，于是把保活间隔拼命调短 —— 这既没用，还可能因为频繁动作更容易触发风控。先分清形态：

| 形态 | 日志特征 | 真实原因 |
|------|----------|----------|
| **网络层断流** | `EventChecker Failed ... {"result": 1006514, "errMsg": "网络连接异常!"}`，随后 `账号状态变更为离线`，**没有** `KickedOffLine` | NAT / 路由器回收空闲长连接、WiFi 抖动、休眠断网 |
| **服务端踢线** | `[KickedOffLine] [下线通知] 你的账号当前登录已失效，请重新登录。` | 同号在别处登录（手机切号最常见）、风控判定异常 |
| **僵死态** | `CheckLoginStatus` 返回 `isLogin: true` 但 `loginError: "登录态已失效"`；`get_status` 仍是 `online: true` | 登录态已废，客户端却没意识到，**收不到也发不出** |

### 关于"23 分钟阈值"

早期版本上确实能观察到"约 23 分钟无消息就被踢"，但我们在连续几天里记录了 6 次真正的 `KickedOffLine`，**全部发生在正在聊天的时段** —— 最近一次距上一条保活消息只有 4 分钟。

结论：**静默被踢不是主因**，把保活间隔调到 3 分钟也救不了"手机切号"造成的踢线。这直接决定了 v2 的设计：保活放宽到 30–45 分钟，主要作为健康探针；真正防踢靠"同号不同时在线"和"分场景恢复"。

---

## 二、为什么本地 API 调用不能保活

NapCat 暴露了 OneBot11 HTTP API（`get_status`、`get_config` 等）。很多人第一反应是"定时调一下 API 不就能保活了吗？"

**实测不行。** 这些调用是 NapCat 在**本地**处理的（`你的程序 -> 127.0.0.1:3000 -> NapCat 内部函数`），只读本地内存状态，**不会向腾讯服务器发送任何数据**。服务器侧看到的依然是"没有活动"。

---

## 三、为什么"给自己发消息"可以保活

真实的消息收发会经过腾讯服务器。要造一条真实消息又不打扰别人，关键观察是：

> NapCat 登录后，**机器人自己的 QQ 号在自己的好友列表里**，可以向自己发起私聊。

```json
POST http://127.0.0.1:3000/send_private_msg
{ "user_id": "机器人自己的QQ号", "message": "check" }
```

返回 `retcode = 0` 表示成功。这条消息：

1. 真正经过腾讯服务器（产生协议活动）；
2. 只发到机器人自己的私聊，**不打扰任何好友 / 群**；
3. **兼做健康探针** —— `retcode != 0` 说明连接已经死了，比 `get_status` 翻牌早得多（`get_status` 可能"假在线"几十分钟）。

v2 默认 **30–45 分钟**随机一条。更短的间隔不会提高稳定性，只会让行为更像脚本。

---

## 四、看门狗的检测：三个信号一起看

只看 `get_status.online` 是不够的 —— 11-11 那次长连接断掉后，它继续报 `online: true` 整整 **50 分钟**。所以 v2 同时看三个信号：

1. **`get_status.online`**：最基础，但会假在线；
2. **`CheckLoginStatus.loginError`**：能识别"僵死态"（`isLogin: true` + `登录态已失效`）；
3. **NapCat 自己日志里的发送失败**（`网络连接异常` / `EventChecker Failed`）：最早、最准的信号，600 秒内出现 2 次就判定连接已死。

每 20 秒一轮，连续 2 次异常才动手。

## 五、恢复逻辑：先判场景，再从轻到重

```
NapCat 在运行吗（WebUI 6099 通不通）？
   │
   ├─ 不通 ──→ 根本没运行（开机 / 崩溃）→ 立即启动，不空等
   │
   └─ 通 ──→ 登录态是什么状态？
              ├─ isLogin=false 或 未登录 ─────→ 扫码流程（见下）
              ├─ isLogin=true 但 loginError 含"失效/重新登录"
              │        └─→ 僵尸态：RestartNapCat → 等缓存登录(240s)
              └─ 正常登录但 get_status 离线 ──→ 分阶段恢复：
                        Phase A  宽限期 90s        —— 网络抖动自愈
                        Phase B  SetQuickLogin ×2  —— 被踢但登录态仍有效
                        Phase C  RestartNapCat     —— 重启 worker，保留 QQ 与登录票
                                  · 等登录 240s，每 90s 补一次快速登录
                        Phase D  全量重启（精确杀进程树 + 重新注入）
                                  · 等登录 480s
                        兜底     弹窗 + 写状态文件，等人扫码
```

设计原则：

- **能轻就不重**：大部分短暂离线会自动恢复，强杀进程反而让快速登录凭证失效、逼你扫码；
- **登录态失效就别空转**：直接喊人扫码；
- **等待要够长**：缓存 token 登录实测偶尔要 2–5 分钟，早期只等 150 秒就判失败，白多出一次扫码；
- **绝不误伤**：只杀 NapCat 自己拉起的进程树（`NapCatWinBootMain.exe` 的后代），桌面 QQ 一根手指都不碰。

## 六、安全阀：别把自己送进风控

社区里"越挂越容易被踢、最后账号被冻结"的案例，绝大多数是**守护脚本自己造成的**：

- 靠扫（累积的）日志关键字判断状态 → 历史命中 → 误判离线；
- 误判后每几分钟杀一次进程 → 连续无效登录尝试；
- 腾讯风控把这种模式识别为"外挂/异常"，轻则频繁踢线，重则冻结。

v2 的对策：

| 机制 | 值 | 说明 |
|------|----|------|
| 单次恢复 | `$MAX_RECOVER = 1` | 一次掉线只自动救一次 |
| 熔断 | `$CIRCUIT_MINUTES = 120` | 救不回来就停手 2 小时，等人处理 |
| 夜间静默 | `02:00–07:00` | 风控高发时段，最多每 3 小时尝试一次 |
| 不杀桌面 QQ | `$FOREIGN_WAIT_MIN = 30` | 检测到用户手动开的 QQ 就先推迟恢复 |
| 无窗口 | `CreateNoWindow` | 关窗口不会连带杀死机器人 |

## 七、登录态与快速登录的几个坑

- **登录态有效**时：被踢后 `SetQuickLogin` 一般可以免扫码重新上线。
- **登录态失效**时：`SetQuickLogin` 返回 `code = -1`，只能扫码。
- **会话已建立时重复调用 `SetQuickLogin`**：会触发 `onUserLoggedIn` 回调，该回调只设置错误文案、不真正置上线，形成"底层似登录、逻辑未上线"的僵死态。守护脚本只在确认离线时调用，调用后必须用真实在线状态复核。
- **缓存 token 登录需要时间**：worker 重启后等 240 秒、全量重启后等 480 秒，期间每 90 秒补一次 `SetQuickLogin`。

---

## 八、桌面 QQ 与机器人的互踢

两者是同一个 `QQ.exe`、同一份用户数据目录（`%APPDATA%\QQ`），Electron 的单实例锁让它们互踢。NapCat 4.18+ 支持 `NAPCAT_QQ_DATA_DIR`，把它指到独立目录即可让机器人拥有自己的 QQ 数据，与桌面 QQ 完全独立（代价：切换时需重新扫码一次）。

在没隔离的情况下，守护脚本会检测"非 NapCat 拉起的 QQ"并推迟恢复最多 30 分钟，但两边仍会周期性互顶。

---

## 九、网络抖动与被踢的区别

| 现象 | 网络抖动 | 被踢下线 |
|------|----------|----------|
| 典型报错 | `1006514 网络连接异常` | `KickedOffLine 登录已失效` |
| 登录态 | 通常还在 | 已失效 |
| 恢复方式 | 网络恢复后自动重连，或重启 worker 复活连接 | 快速登录 / 扫码 |
| 守护脚本动作 | 先等 90 秒；发送失败探测可提前重启 worker | 快速登录 → 重启 → 扫码 |

区分这两者，是"恢复动作该轻还是该重"的关键。
