# 原理说明

本文解释"为什么会被踢"以及"保活和看门狗为什么有效"。

---

## 一、为什么空闲一段时间会被踢

QQ 客户端与腾讯服务器之间需要维持一条**长连接**（心跳 + 消息活动）。对于第三方协议（NapCat 等），腾讯会额外判断其行为是否"像真人"：

- 如果长时间**没有任何真实的消息收发**，风控会认为这个会话"异常"或"已无人使用"；
- 达到阈值后，服务端强制让登录失效，客户端收到：

```
[KickedOffLine] 你的账号当前登录已失效，请重新登录。
```

在本方案的实测环境中，这个阈值约为 **23 分钟**。注意：不同账号、不同环境可能有差异，它不是固定值，所以保活间隔要留足安全余量。

---

## 二、为什么本地 API 调用不能保活

NapCat 暴露了 OneBot11 HTTP API（如 `get_status`、`get_config`）。很多人第一反应是"那我定时调一下 API 不就能保活了吗？"

**实测不行。**

原因：这些 API 调用是 NapCat 在**本地**处理的（`你的程序 -> 127.0.0.1:3000 -> NapCat 内部函数`），它只是读取本地内存里的状态，**不会向腾讯服务器发送任何数据**。服务器侧看到的依然是"没有活动"，所以照样踢。

---

## 三、为什么"给自己发消息"可以保活

真实的消息收发会经过腾讯服务器。要造一条真实消息，又不打扰别人，关键观察是：

> NapCat 登录后，**机器人自己的 QQ 号在自己的好友列表里**，可以向自己发起私聊。

调用：

```json
POST http://127.0.0.1:3000/send_private_msg
{ "user_id": "机器人自己的QQ号", "message": "19:30  ok" }
```

返回 `retcode = 0` 表示成功。这条消息：

1. 真正经过腾讯服务器（产生协议活动，重置"空闲计时器"）；
2. 只发到机器人自己的私聊，不会打扰任何好友 / 群。

于是只要每隔**小于被踢阈值**的时间发一条，就能一直保持在线。我们用 10–17 分钟随机值，既留了余量，又避免固定间隔显得机械。

---

## 四、看门狗的恢复逻辑：先判断场景，再对症处理

保活能大幅降低被踢概率，但不能保证 100% 不掉线（开机没拉起、网络抖动、QQ 卡死、登录态失效都可能发生）。所以还需要看门狗。

### 检测

- 每 20 秒调用一次 `get_status`；
- 连续 2 次离线（约 40 秒）才判定为"需要恢复"，避免单次抖动误判。

### 第一步：先判断当前是什么场景

守护脚本不是一上来就按固定流程杀进程，而是先确认 NapCat 到底在不在、登录态还在不在：

```
get_status 不通？
   │
   ├─ WebUI(6099) 也连不上 ──→ NapCat 根本没运行（开机/崩溃）
   │                              → 立即启动 NapCat，不空等
   │
   └─ WebUI 连得上，但登录态明确失效 ──→ 立即刷新二维码 + 弹窗，等人扫码
                                          （自动恢复注定失败，不再反复强杀）
```

### 第二步：NapCat 在运行、只是掉线 → 从轻到重处理

只有"NapCat 已经在跑、原本在线"的情况，才走下面的分阶段流程：

```
Phase A  宽限期(90s)          —— 网络抖动，先等它自愈
   │ 仍离线
Phase B  进程内快速登录(2次)   —— 被踢但登录态有效，最轻量
   │ 仍离线
Phase C  RestartNapCat        —— 重启 worker，不杀 QQ
   │ 仍离线
Phase D  彻底重启 QQ           —— 最暴力，放最后
   │ 仍离线
兜底      刷新二维码 + 弹窗    —— 登录态失效，需要人工扫码
```

设计原则：

- **先分清场景**：开机没运行就直接拉起，登录态失效就直接喊人，不在这两种情况下空等/乱杀；
- **能耐心等待就等待**：大部分短暂离线是网络问题，会自行恢复；
- **能不杀进程就不杀**：重启 QQ 成本最高，且可能让快速登录凭证失效；
- **失败有上限**：连续自动恢复超过次数就停下来等人，避免反复横跳。

---

## 五、登录态与快速登录的几个坑

- **登录态有效**时：被踢后调用 `SetQuickLogin` 一般可以免扫码重新上线。
- **登录态失效**时：`SetQuickLogin` 会返回 `code = -1`，无法免扫码，只能重新扫码。
- **会话已建立时重复调用 `SetQuickLogin`**：会触发 `onUserLoggedIn` 回调，该回调只设置错误文案、不真正置上线，可能造成"底层似登录、逻辑未上线"的卡死中间态。因此守护脚本只在确认离线时调用，并在调用后用 `get_status` 复核真实在线状态。

---

## 六、网络抖动与被踢的区别

| 现象 | 网络抖动 | 被踢下线 |
|------|----------|----------|
| 典型报错 | `1006514 网络连接异常` | `KickedOffLine 登录已失效` |
| 登录态 | 通常还在 | 已失效 |
| 恢复方式 | 网络恢复后 QQ 自动重连 | 快速登录或扫码 |
| 守护脚本动作 | 宽限期等待 | 进入快速登录 / 重启 |

区分这两者，是"恢复动作该轻还是该重"的关键。
