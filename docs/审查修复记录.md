# 代码审查与修复记录

一次完整审查（约 2400 行 PowerShell + JavaScript）的结果。行号指**修复前**的生产版本，
括号里是文件。严重度：🔴 会导致错误行为 / 🟡 隐患 / 💭 噪音与体验。

## 一、通知中文变 `?`（本次的直接起因）

| # | 位置 | 严重度 | 问题 | 修复 |
|---|------|--------|------|------|
| F1 | `guardian.ps1:171-173` `Send-Notification` | 🔴 | `Invoke-RestMethod -Body $body` 传**字符串**且未声明 charset，.NET 退化为 ASCII 编码，每个汉字变成 `?`，`Content-Length` 恰好等于字符数 | `[Text.Encoding]::UTF8.GetBytes($body)` + `-ContentType 'text/plain; charset=utf-8'` |
| F2 | `guardian.ps1:179` 新增 `ConvertTo-NtfyHeaderText` | 🟡 | ntfy 的 `Title` 请求头只能是 ASCII，中文标题会让整个请求失败 | 非 ASCII 转 RFC 2047 `=?UTF-8?B?<base64>?=` |
| F3 | `guardian.ps1:794-795` `Send-KeepAlive` | 🟡 | 同一个坑：OneBot `send_private_msg` 的 JSON 正文现在恰好纯 ASCII，一旦消息带中文就同样变 `?` | 同样改成 UTF-8 字节 + `application/json; charset=utf-8` |

**关键是"只加 ContentType 不够"**：实测 `-ContentType 'text/plain'`（不带 charset）仍然
发出 69 字节的 `?`。必须**既传字节又声明 charset**。对照实验（本地 TcpListener 抓 hex）：

| 写法 | Content-Type | Content-Length | 正文 |
|------|--------------|----------------|------|
| `-Body $str` | `application/x-www-form-urlencoded`（默认） | 69 | `3f 3f 3f 20 51 51 ...` 全是 `?` |
| `-Body $str -ContentType 'text/plain'` | `text/plain` | 69 | 仍是 `?` |
| `-Body $bytes -ContentType 'text/plain; charset=utf-8'` | `text/plain; charset=utf-8` | 111 | `e6 9c ba e5 99 a8 ...` = 机器人 ✅ |

验证：修复后实发一条到自己的 ntfy 主题，再 `?poll=1&since=all` 回读，得到
`中文编码测试：机器人 QQ 已自动恢复在线（无需扫码）`、`emoji: ✅ 制表: ①②③`，全部正确。

## 二、可靠性问题

| # | 位置 | 严重度 | 问题 | 修复 |
|---|------|--------|------|------|
| F4 | `guardian.ps1:845-851` 单实例接管 | 🔴 | 心跳里的 PID 直接 `Stop-Process -Force`；PID 被系统回收给别的进程时会误杀（最坏情况是 QQ） | 先 `Get-CimInstance Win32_Process` 取 `CommandLine`，确认含 `guardian.ps1` 才杀，否则只记一行日志并接管 |
| F5 | `guardian.ps1:666-688`、`731-753` | 🔴 | Phase A（90 s）、Phase B（60 s）、`Wait-Scan`（最长 10 min）等长循环里从不写心跳 → 心跳看起来"僵死 3 分钟以上"，另一个实例会判定前者死掉并杀掉正在恢复的实例 | 4 处等待循环内补 `Write-Heartbeat`；`Write-Heartbeat` 定义提前到 Logging 段 |
| F6 | `guardian.ps1:364-414` `Read-NewNapCatLog` | 🔴 | 首次读到日志文件时偏移从 0 开始 → **重放几天前的历史日志**，把旧的"网络连接异常"当成刚刚发生，凑够 2 条触发假 connection reset，并污染 `kick.log` | 首次见到文件时把偏移设成文件末尾 |
| F7 | `guardian.ps1:376` 同上 | 🔴 | `if ($f.Length -le $pos) { return }`：NapCat 重启会重建日志文件，`Length` 从此永远小于旧 `pos`，**发送失败探测永久失明**且毫无提示 | `Length -lt $pos` 时把偏移归零并继续读；只有相等才 return |
| F8 | `guardian.ps1:813-823` 互斥体 | 🟡 | 上一个实例被强杀后 `WaitOne(0)` 抛 `AbandonedMutexException`，被当成"没拿到" → 降级到 Local 互斥体，可能出现两个实例并存 | 显式 `catch [System.Threading.AbandonedMutexException] { $gotMutex = $true }`（内核此时已把所有权交给当前进程） |
| F9 | `guardian.ps1:182-192` `Get-NapCatLastActivity` | 🟡 | 找不到日志目录时 `return (Get-Date)` → 空闲时长恒为 0 → 保活探针永远不发 | 返回 `[DateTime]::MinValue` |

## 八、看过但**不修**的（附理由）

| 位置 | 现象 | 为什么不修 |
|------|------|-----------|
| `guardian.ps1` WebUI 每轮一次 `/api/auth/login` | 约 3 次/分钟 | NapCat `loginRate` 默认 10，够用；做凭据缓存反而会在 token 过期时误判"NapCat 没运行"并重复拉起 |
| `guardian.ps1` 的 `Notify-Admin` 30 分钟去重 | 同一次故障可能少一条通知 | 防止刷屏的收益更大，且 `Wait-Scan` 失败时主循环会补 |
| `qrsync.js` `readQr()` 里 40 ms 忙等 | 一个请求周期占用 CPU | 单用户场景影响可忽略；改成事件驱动要引入 `fs.watch` 的跨平台坑 |
| `/close` 端点 | 持密钥者可停服 | 设计如此（扫完码就该关） |
| 本地 OneBot HTTP 无 token | 无鉴权 | 只监听 `127.0.0.1` |
| `daemon.ps1` 用 `ngrok config add-authtoken` 写全局配置 | token 落到 `%LOCALAPPDATA%\ngrok\ngrok.yml` | 改环境变量方案未验证，改错会断掉正在等扫码的隧道，风险大于收益；已在 qrsync README 注明 |
