# 代码审查与修复记录

一次完整审查（约 2400 行 PowerShell + JavaScript）的结果。行号指**修复前**的生产版本，
括号里是文件。严重度：🔴 会导致错误行为 / 🟡 隐患 / 💭 噪音与体验。

## 一、通知中文变 `?`（本次的直接起因）

| # | 位置 | 严重度 | 问题 | 修复 |
|---|------|--------|------|------|
| F1 | `guardian.ps1:171-173` `Send-Notification` | 🔴 | `Invoke-RestMethod -Body $body` 传**字符串**且未声明 charset，.NET 退化为 ASCII 编码，每个汉字变成 `?`，`Content-Length` 恰好等于字符数 | `[Text.Encoding]::UTF8.GetBytes($body)` + `-ContentType 'text/plain; charset=utf-8'` |
| F2 | `guardian.ps1:179` 新增 `ConvertTo-NtfyHeaderText` | 🟡 | ntfy 的 `Title` 请求头只能是 ASCII，中文标题会让整个请求失败 | 非 ASCII 转 RFC 2047 `=?UTF-8?B?<base64>?=` |
| F3 | `guardian.ps1:794-795` `Send-KeepAlive` | 🟡 | 同一个坑：OneBot `send_private_msg` 的 JSON 正文现在恰好纯 ASCII，一旦消息带中文就同样变 `?` | 同样改成 UTF-8 字节 + `application/json; charset=utf-8` |

**关键是"只加 ContentType 不够"**：实测 `-ContentType 'text/plain'`（不带 charset）仍然
发出 69 字节的 `?`。必须**既传字节又声明 charset**。对照实验（本地 TcpListener 抓 hex）：

| 写法 | Content-Type | Content-Length | 正文 |
|------|--------------|----------------|------|
| `-Body $str` | `application/x-www-form-urlencoded`（默认） | 69 | `3f 3f 3f 20 51 51 ...` 全是 `?` |
| `-Body $str -ContentType 'text/plain'` | `text/plain` | 69 | 仍是 `?` |
| `-Body $bytes -ContentType 'text/plain; charset=utf-8'` | `text/plain; charset=utf-8` | 111 | `e6 9c ba e5 99 a8 ...` = 机器人 ✅ |

验证：修复后实发一条到自己的 ntfy 主题，再 `?poll=1&since=all` 回读，得到
`中文编码测试：机器人 QQ 已自动恢复在线（无需扫码）`、`emoji: ✅ 制表: ①②③`，全部正确。

**实测验证**：`-TestNotify` 邮件送达；ntfy 超时后自动降级成功；互斥体二次启动返回
`exit code 0` 且日志写 `mutex is held but heartbeat is missing - exiting to be safe.`；
`Parser::ParseFile` 0 错；1315 行版本连续运行 6 小时无异常。

**已知取舍（2026-11-15 已调整）**：检测依然需要"有发送行为"才会产生日志，因此最坏延迟 =
下一次探针间隔。早期版本是 20–40 分钟随机，实测有一次假在线因此拖了 49 分钟；现在改成
**固定 10 分钟**（`$KEEPALIVE_MIN = 600`、`$KEEPALIVE_IDLE_MIN = 10`、取消夜间静默），
把最坏发现时间压到 10 分钟，代价约 144 条自发消息/天，不进 LLM、不耗 token。
