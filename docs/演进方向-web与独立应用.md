# 演进方向：要不要做成网页前端 / 独立软件？

结论先放前面：

- **网页面板值得做**（约 3–5 人日），而且成本几乎为零 —— `scripts/qrsync/qrsync.js`
  已经是一个带密钥鉴权的常驻 HTTP 服务，还有公网隧道，扩一个 `/api/status` 就是面板。
- **独立软件（Electron / Tauri 安装包）不值得做**。核心依赖是"Windows + 桌面版 QQ +
  NapCat + 计划任务 + 管理员权限"，打包成 exe 一个都去不掉，却要额外背上签名、杀软误报、
  自动更新三条长期债务。
- 想要"像软件"的观感，性价比最高的两条捷径：**托盘图标**（0.5 人日）和
  **PWA**（把网页"添加到主屏幕"，成本≈0）。

## 一、形态对比

| 形态 | 工作量 | 主要成本 | 收益 | 结论 |
|------|--------|----------|------|------|
| A. 现状：脚本 + 日志 + 通知 | 0 | 无 | 能自愈、能告警，但看状态得坐到电脑前 | 保留为内核 |
| B. 本地网页面板（扩展现有 qrsync 服务） | 3–5 人日 | 一个聚合接口 + 一个静态页 | 手机随时看状态/二维码/最近事件，一键触发重启 | ✅ 推荐 |
| C. Tauri 桌面应用 | 10–15 人日 | Rust 侧封装、UAC 提权、签名、自动更新 | 双击安装、托盘常驻 | ❌ 收益不抵成本 |
| D. Electron 桌面应用 | 8–12 人日 | 100 MB+ 体积、原生模块重编译、签名、更新 | 同上，且更重 | ❌ |
| E. 云端 SaaS（多用户托管） | 不可行 | 需要真实 Windows 桌面 QQ 扫码登录，无法容器化，且多账号托管直接撞腾讯风控 | — | ❌ 前提不成立 |

成本按"熟悉这套代码的人"估，不是外包报价。

## 二、B 的最小设计（复用现有骨架）

`qrsync.js` 现在只做一件事：把 `qrcode.png` 吐成网页。它已经有密钥鉴权
（`timingSafeEqual`）、有公网隧道、有守护进程，**面板只是多几个路由**：

```
GET  /api/status?k=<key>    → {
        guardian: { pid, heartbeat_age_sec, alive },
        login:    { state, uin_mask, updated_at },   # 来自 login-state.json
        napcat:   { online, webui_up, owned_pids },
        events:   [ 最近 N 条 guardian.log / kick.log，已脱敏 ],
        qr:       { present, mtime }
      }
POST /api/relaunch          → 写 force-relaunch.flag（guardian 下一轮自己处理）
POST /api/keepalive         → 让 guardian 立刻发一次探活
```

要点：

1. **不要引入构建链**。一个 `index.html` + 原生 JS + 30 秒轮询足够；引入 React/Vite
   会立刻产生 node_modules、构建产物、版本锁三件套，与"单文件脚本"的定位冲突。
2. **动作类接口用请求头传密钥**（`X-QR-Key`），而不是 `?k=`。URL 会进浏览器历史、
   隧道访问日志、Referer。
3. **动作类接口必须限速 + 仅接受 POST**。`/api/relaunch` 暴露在公网隧道上，等于把
   "重启机器人"这个动作挂到了互联网；24 位随机密钥够用，但加个每 IP 每分钟 3 次的
   粗限速几乎零成本。
4. **面板只读日志尾部，不要读全量**。`guardian.log` 可能已经几十 MB，读全量会让
   面板自己变成故障源（这个坑在守护脚本里刚踩过一次，见 `docs/审查修复记录.md` F6/F7）。
5. 手机端优先：二维码要能点开放大，状态用颜色区分（绿=在线/黄=恢复中/红=需要扫码）。

## 三、为什么不做独立软件

1. **依赖一个都去不掉。** 机器人能不能上线，取决于 NapCat 能不能用桌面版 QQ 的登录票，
   而 QQ 需要完整的 Windows 桌面环境。装个 exe 并不会让二维码消失、也不会让风控变松。
2. **分发成本远大于开发成本。** 未签名的 exe 在 Windows 上 100% 触发 SmartScreen 警告，
   杀软（尤其是"行为像看门狗/注入进程"的程序）误报率极高。代码签名证书约 $100–400/年，
   还得处理时间戳服务和续期。这个项目的用户量大概率是"自己和几个朋友"。
3. **维护成本是持续的。** Electron/Tauri 的版本升级、原生模块重编译、自动更新通道、
   崩溃上报…… 而现在的形态上线一次的成本是"改一行脚本 + 重启计划任务"。
4. **排障更难。** 出问题时用户能发给你的是一段 `.ps1` 和一份文本日志；换成打包应用，
   你要面对的是"日志在哪、怎么开 debug、装的是哪个版本"。

## 四、如果就是要"像个软件"

按性价比排序：

1. **PWA（0 成本）**：给面板加 `manifest.json` + service worker，手机"添加到主屏幕"后
   有图标、全屏、可离线打开 shell。体感与 App 的差别只剩"没有推送"——而通知已经有 ntfy 了。
2. **托盘图标（0.5 人日）**：`System.Windows.Forms.NotifyIcon` 或 `BurntToast`，
   托盘菜单放"立即重启 / 打开扫码页 / 查看日志 / 暂停守护"。这一个功能就覆盖了
   独立应用 80% 的日常价值。
3. **单文件安装器（1 人日）**：现有的 `install_guardian.bat` 已经做了一半；
   补上"检测 NapCat 路径 + 写配置 + 注册计划任务 + 自检"就是完整体验，且不产生签名负担。

真正需要独立应用的场景只有一个：**给完全不懂命令行的第三方用户分发**。如果哪天要做，
也应该基于 Tauri（体积小、无 Node 运行时），并且先把上面三条捷径都做完再评估 ——
大概率做完就发现不需要了。
