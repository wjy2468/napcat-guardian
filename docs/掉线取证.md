# 掉线取证：这些账号到底是怎么被踢的

> 结论先行：**日志里其实有两种完全不同的掉线**，被混在一起讨论就会得出错误结论——
> 一种是被腾讯吊销会话（`[KickedOffLine]`，必须重新扫码或等缓存票），
> 另一种是自己的 QQ 长连接悄悄死掉（`1006514 网络连接异常!`，客户端还以为自己在线）。
> 前者集中在 **109–121 分钟** 的会话寿命上，后者出现在 **活得更久** 的会话里。

本文的每个数字都能在你的机器上复现，命令见文末。

## 2. 三条能站住的判断

1. **踢线不是"闲太久"引起的**。被踢前 5 分钟的发送量中位只有 2 条，但也有正在活跃聊天时被踢的（11-15 12:38 前 2 分钟还在发群消息）。间隔从 0 到 34 分钟都有 → 与静默时长无关，与**会话年龄**强相关。
2. **踢线也不是本机断网**。每次被踢前后的 `WLAN-AutoConfig` / `Dhcp-Client` 都是空事件，公网自检也没有失败记录；`kick.log` 里的 IP 一直是同一个。
3. **"活到 2 小时"和"被踢"高度重合，但不是硬 TTL**：有 4 次会话活过了 120 分钟（最长 252 分钟），它们没有收到 `[KickedOffLine]`，而是死在假在线上。所以更像是「票据到期 → 客户端尝试续期 → 续期成功就继续活，失败就被踢」——被踢的 109–121 分钟是**续期失败的截面**。

## 3. 还没被证伪的猜想

| 猜想 | 现状 | 怎么验证 |
|---|---|---|
| 登录票据约 2 小时寿命，续期失败即被踢 | 与 10 次密集分布吻合，但 4 个长会话说明不是硬上限 | 做 `o3HookMode` 1→0 单变量实验，比较会话中位时长（`experiment-compare.ps1`） |
| 长会话的假在线是 NAT/运营商回收空闲连接 | 与"无网络事件、无踢线、只有发送失败"一致 | 换网络（热点↔家宽）对比，或缩短探针间隔后看是否更难发生 |
| 客户端指纹/注入被判外挂 | 没有任何直接证据（日志无提示） | 只能靠 `o3HookMode`/版本组合的对照实验 |
| 手机同号多端 | 用户已确认每次扫完码都退出登录 | 观察"退出登录"后踢线是否减少 |

## 4. 为什么这套取证比"数重启次数"有用

- 重启次数受**恢复策略**影响（熔断、夜间静默、快速通道），同一套账号在不同配置下数字会变；
- 会话寿命只受**服务端**影响，是真正能用来比较实验组的指标；
- 所以 `kick-report.ps1` 输出的 `median` 才是实验的判据，`experiment-compare.ps1` 用它来给结论。

## 5. 复现命令

```powershell
# 14 次被踢的会话时长、检测耗时、恢复路径
.\scripts\kick-report.ps1

# 存快照，供实验前后对比
.\scripts\kick-report.ps1 -Json | Set-Content D:\napcat\baseline.json -Encoding UTF8

# 看日志覆盖窗口（自己写几行也行，关键是"会话起点 → 结尾方式"）
Get-ChildItem D:\napcat\NapCat.Shell\logs\*.log |
  ForEach-Object { "$($_.Name)  $($_.LastWriteTime)" }
```

> 前提：NapCat 的 `fileLog` 必须打开（`config\napcat.json` 里 `"fileLog": true`）。
> 关着的时候这些证据一条都不会有——这也是"为什么以前只能靠猜"的根本原因。

## 附：为什么有时重启就能免扫码，有时必须扫

同一个"登录态已失效"，恢复结果并不总是相同。三次实测：

| 时间 | 动作 | 结果 |
|---|---|---|
| 11-15 12:52 | 被踢后**全量重启**（新 QQ 进程） | `logged in.` —— 磁盘上的票据还有效，免扫码 |
| 11-15 13:03 | 会话 123 分钟时 **RestartNapCat**（只重启 worker） | 240 秒内两次补快速登录全失败 → 停在二维码 |
| 11-15 13:08 | 紧接着**全量重启** | 仍是二维码 —— 票据已被上一步用掉/作废 |

原因是两条路径依赖的东西不同：

- **全量重启**：拉起新的 QQ 进程，它从磁盘（`...\Roaming\QQ\auth\login.enc` 一类）读取上次的登录凭据，有机会直接续上。
- **RestartNapCat**：只重启 NapCat 的 worker，靠的是进程内存里的会话票据。被踢之后内存里那份已经失效，所以这条路在"踢线"场景**基本必然失败**。

补充证据：`POST /api/QQLogin/GetQuickLoginList` 返回 `{"code":0,"data":[]}` —— 本机**没有保存任何快速登录票**，所以也不存在"快速登录直接续上"的可能。

由此得到的操作结论（已写进守护脚本的快速通道）：

1. 确认是 `[KickedOffLine]` 而不是网络问题后，**跳过 Phase A/B/C，直接全量重启一次**。
2. 只做**一次**。第一次失败就不要再来第二次——每多试一次都可能把剩下的凭据作废，最后一定要人工扫码。
3. 全量重启仍失败时，立刻停下等扫码，并把二维码发出去（守护的 `need_scan` 分支）。

> 想看历史每次都走了哪条路：`scripts\kick-report.ps1` 的 `path` 列会标 `fast`（跳过 A/B/C）或 `staged`（走了完整四阶段），`recoverSec` 是检测到被人扫回来的耗时。
